# ADR 001: private Creator Studio foundation

Date: 8 October 2026. Status: accepted for the local foundation slice; production authentication and hosting remain unconfigured.

## Decision and reason

Keep the modular Python application, useful agent stages, SQLite collection archive and existing Studio. Add small versioned contracts and a private repository boundary before the UI redesign. The current unauthenticated Firebase derived path and public-file fallback cannot be the factual or authorization boundary for an evidence-first creator system.

Use platform-neutral source/story/evidence objects as the factual core. A LinkedIn content variant references that core; it does not become the master factual article. Preserve the five existing pipeline collections through an explicit compatibility layer and additive migrations. Stable legacy IDs, source links, schedules, publication records and owner edits take priority over new naming.

Local/offline private state belongs in ignored `.studio-private/pipeline.json`, outside `docs/` and version control, with atomic writes, backend revisions, safe imports, backups and dry-run reports. For the first slice, `studio_server.py` serves the existing Studio over loopback through Flask (an existing dependency), and provides `/api/session` login/logout, `GET /api/state`, and conditional `PATCH /api/records/<collection>/<id>` using `expected_revision`. The browser receives a private-API configuration marker, not baked-in private state or credentials. Session cookies are HttpOnly and SameSite Strict; Host, Origin and `X-Studio-CSRF` checks protect the private boundary. This implementation must pass its tests before it is recorded as complete.

The browser cache is pending local work, not another master or an implicit public export. Existing static/legacy Firebase code remains during this local slice because switching a deployed database without verified owner authentication and a tested live migration would risk owner data and access. Its known authorization weakness remains explicitly unresolved. The new authenticated loopback workflow is the safe path for local private work; it is not a production authentication retrofit for the existing static site.

Evaluate owner-scoped Firebase Authentication and denied-by-default rules as the default deployed store path because Firebase already exists. An installed API credential, Firebase URL or passcode is not proof of owner authorization. A local authenticated bridge is a development option, not a claim that static GitHub Pages now has a secure backend. Choose and document one server/worker hosting boundary before deployed integration; avoid permanent Firebase/file dual writes.

Manual prompting, copy/export and owner-confirmed posting remain the delivery default. Paid text/image providers and publishing adapters remain disabled or unavailable until separately configured and authorized. Future platform contracts expose real capability states; no fake connected accounts.

Implementation references: [Flask security guidance](https://flask.palletsprojects.com/en/stable/web-security/) covers cookie flags, expiry, CSRF and Host checks; the installed Flask 3.0.3 uses an explicit loopback Host guard instead of the newer `TRUSTED_HOSTS` setting. [Firebase rule conditions](https://firebase.google.com/docs/database/security/rules-conditions) describe authenticated identity for the later deployed boundary. These references informed the boundary; they do not constitute an audit of live rules.

## Dependency choices

- Continue with the existing Python/JavaScript architecture. No frontend framework replacement, agent framework, microservices, queue, vector database or event bus is needed for this slice.
- Keep `news.db` as the archive. Private editorial state has a separate ownership/lifecycle because hourly collection rewrites the archive and public artifacts.
- Prefer standard-library validation/storage primitives and the existing Flask dependency for the first deterministic slice, keeping contracts independent of provider SDKs. If another library becomes necessary, record its concrete validation or concurrency benefit and test it before adding it.
- Firebase SDK/rules emulator work follows the local contracts and safety tests. Secrets, OAuth tokens and provider credentials belong on a server, never in generated HTML, prompts or browser storage.
- Build a verified evidence model before strengthening writer prompts; complete revision/approval guards before durable delivery. A later UI shell must display the real states supplied by these boundaries.

## Sequence and acceptance

| Phase | Acceptance gate |
| --- | --- |
| 0: inventory/baseline | Code/data map, reproduced source gaps, baseline tests and private migration/rollback plan recorded |
| 1: private state/contracts | Existing owner data survives tested migration; unauthorized access denied; private browser path, revisions/conflicts and backup/rollback verified |
| 2: shared Studio UI | Existing routes/manual workflow work in both themes/narrow layouts with keyboard and honest sync states |
| 3: discovery/evidence | Event-aware dedupe, safe bounded retrieval, meaningful dates/outcomes and source evidence references tested |
| 4: prompts/verification | Shared API/manual policy, strict import review, numeric/attribution traps, owner-note provenance and stale approvals tested |
| 5: assets | No-image decision/import/template flow and approved content-revision provenance verified |
| 6: LinkedIn completion | Complete manual journey/reminders/confirmation; guarded jobs and budgets; optional publishing stays off until authorized |
| 7: learning/extensions | Observed feedback and alternate-format test adapter reuse the evidence core |

The first slice changes local private state, contracts and safe compatibility plumbing. Deferring deployed authentication is an environment/integration boundary, not completion of Phase 1. Continue Phase 1 before cosmetic redesign or evidence/publishing activation.

## Consequences and rollback

Static Studio can still browse its built-in public news and retain owner work locally; cross-device private sync needs its configured authenticated service. Removing an unsafe fallback can surface an explicit configuration/error state. That state must preserve edits and accurately describe its limit.

Typed contracts and migration metadata do not turn legacy excerpts or status labels into verified evidence/approval. Imported historical records retain their origin and remain subject to later review. Stronger factual checks, a durable daily budget and reliable jobs are still future work.

Foundation code can be reverted independently; private files/backups are preserved separately. Before deploying a storage change, export/backup live state under owner authorization, dry-run migration and verify rollback. Do not deploy rules, migrate live data, buy provider calls or post to accounts during this local slice.
